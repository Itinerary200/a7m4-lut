# 网格蒸馏优化方案（提案，未实施）

> 目标：在**不劣化成品精度**的前提下，把网格蒸馏变快、变省内存、并真正收敛。
> 本文是决策依据，实施前需确认。

## 一、现状实测（QCls，同一份 job，GPU=RTX 4060 / CPU=7945HX）

| 阶段 | GPU（torch 可用） | CPU（无 torch） |
| --- | --- | --- |
| 载入 PC + 渲染原生基准（99,372 行） | 0.2 s | 0.3 s |
| teacher 求值（训练 64,562 + 探针 35,937 = 100,499 行） | 0.4 s | 0.1 s |
| **网格求解（bounded FISTA，1215 系数）** | **6.6 s**（600 迭代，`converged=false`） | **>10 min，峰值 18.6 GB** |
| 整数舍入 refine（1 / 3 sweeps） | 1.6 s / 1.9 s | 同量级 |
| evaluate（100,499 行） | 0.4 s | 0.4 s |
| **合计（数学部分）** | **≈ 11 s** | **> 12 min** |

求解器审计（`grid_report.json` → `fitting.candidates[0].solver`）：

```json
{"solver": "bounded FISTA; resident grid interpolation",
 "iterations": 600, "converged": false,
 "before": 0.02228759042918682, "after": 0.0005473186611197889,
 "regularization": 0.0, "clipping_in_objective": true}
```

**两个结论**

1. GPU 上蒸馏只有 ~11 s，**不是整条管线的时间瓶颈**（瓶颈在拟合阶段）；
2. 但求解器 600 次迭代**没有判收敛**，且 CPU 路径会退化成 18.6 GB / 10 min+ ——
   前者是精度天花板，后者是无 GPU 机器的可用性问题。

## 二、数学事实：网格是线性的

固件渲染（`HybridModel.predict_cpu` / `residual_grid.evaluate`）：

```
y = x + (Σ_i w_i(x)·c_i) · R(x)          # c_i 为节点系数，R(x) 为逐样本 3×3 响应
```

- `w_i(x)`：三线性插值的 8 个非零权重（只依赖 x）
- `R(x)`：只依赖 x，**不依赖 c**

所以对固定 x，`y` 是 `c`（1215 维）的**仿射函数**。无约束最小二乘有闭式解：

```
M c = b,  M = Σ_s A_sᵀ A_s (1215×1215),  b = Σ_s A_sᵀ (t_s − x_s)
```

每个样本 A_s 只有 8 结点 × 3 通道 = **24 个非零项**，M、b 可用分块外积累加组装
（~1e8 次乘加，numpy 秒级），无需任何迭代求解器。

## 三、优化方案

### 方案 A（推荐）：精确 L2 预解 + 短程非线性精修

1. **组装稀疏正规方程**得到无约束最优 `c*`（预计 < 2 s，内存 < 500 MB）；
2. **投影到 ±64**，再做 active-set 修正（贴边系数冻结，余下重解，2–3 轮）；
3. 以 `c*` 为**热启动**，跑 80–120 次真实目标（display cost + clip + 平滑正则）
   的 FISTA/IRLS；
4. 加 `rtol/atol` 早停判据，审计里如实写 `converged`、迭代数、目标值。

**预期**：GPU 6.6 s → ~2 s；目标值低于现网（现网 600 次未收敛）；
`limit_fraction` 可控（贴边比例作为报告项）。

### 方案 B（必做，与 A 独立）：CPU 路径稀疏化

现在无 torch 时 FISTA 走稠密算子（135k×1215 ⇒ 18 GB）。把插值/梯度写成分块稀疏
算子（每块 8 个非零权重），内存降到 < 1 GB、CPU 时间降到 ~20 s。
价值：**没有显卡的机器也能跑完整管线**，也顺便消掉 32 GB 机器"网格阶段必须独占"的限制。

### 方案 C（低成本，先做）：收敛判据 + 迭代预算

把"固定 600 次"改为"目标相对下降 < 1e-4 或达 200 次即停"，审计写清 `converged`。
预计省 30–60% 求解时间，且不再出现"没收敛却照用"的隐性行为。

## 四、验收标准（A/B 必须全过）

| 项目 | 要求 |
| --- | --- |
| 精度 | QCls / P400 / Movus6 的网格档 mae8、ΔE00 **不劣于** 3.08 / 6.58 / 15.66 |
| 一致性 | BIN `decode∘pack` 恒等；解码回放与求解器预测逐样本一致 |
| 时间 | GPU 求解 ≤ 3 s；CPU 求解 ≤ 30 s |
| 内存 | CPU 峰值 ≤ 1 GB（现状 18.6 GB） |
| 审计 | `converged` 必须有真实判据，`limit_fraction`、迭代数入报告 |

## 五、实施顺序与工作量

| 步骤 | 内容 | 预估 | 风险 |
| --- | --- | --- | --- |
| 1 | 方案 C：收敛判据 + 迭代预算 | 1 小时 | 低（只改预算） |
| 2 | 方案 B：CPU 稀疏算子 | 半天 | 中（数值等价性要测） |
| 3 | 方案 A：正规方程预解 + active set + 热启动精修 | 1–2 天 | 中（需 A/B 验证） |

改哪里：只动**本工程**的 `src/r5lut/grid_ls.py`（新增）+ 引擎侧**最小钩子**
（现有 `pc_stages.fit_response_grid` 之前插入预解）。vendor 代码保持可回退。

## 六、不做的事（明确边界）

- 不改固件网格格式（405×±64 分辨率是硬约束，前面的实验已证明它才是精度上限）；
- 不用 PC teacher 换目标（QCls 3.11 / Movus6 15.86，实测无收益且更慢）；
- 不动 `refine_grid` 的整数舍入策略（它对 `limit_fraction` 已有约束作用）。
